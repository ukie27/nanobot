## 1. 文档职责

本文是 CareerConsole 的业务事实源，统一回答以下问题：

- 产品解决什么问题，明确不做什么；
- 用户从建立档案到完成申请、面试和复盘的完整流程；
- 当前每项功能是否已经实现；
- 正式业务数据如何产生、确认、冻结和追溯；
- 如何安装、启动、配置、测试、备份和排障；
- 开发新功能时必须维护哪些业务约束。

代码、数据库迁移和自动化测试是实现事实的最终依据。本文不得把规划写成已完成功能；无法从实际代码和测试确认的能力必须标为“部分实现”或“尚未提供”。

状态定义：

- **已实现**：存在正式代码路径、持久化模型/API，并有相应测试或可执行验证。
- **部分实现**：主流程可用，但仍有明确缺口或交付限制。
- **尚未提供**：只有设想，或没有可用的正式产品路径。

## 2. 产品定位

CareerConsole 是面向个人求职者的本地单用户求职操作台。它把分散的简历、岗位、邮件、申请进度、任务和面试反馈组织成可追溯的业务系统，并使用受控 Agent 完成非结构化信息理解和候选建议。

核心业务链路：

```text
用户资料
  → 个人档案与求职偏好
  → 招聘机会与具体岗位
  → 岗位匹配与每日推荐
  → 简历方向、材料生成与审核
  → 用户在外部网站投递
  → CareerConsole 确认申请并冻结快照
  → 邮件证据、申请事件、日程和任务
  → 面试准备、复盘和成长项
  → 已确认改进项回流可信上下文
  → 自动持续职业诊断与下一步建议
```

CareerConsole 不是：

- 自动批量投递或自动联系招聘方的机器人；
- 完整邮件客户端；
- 企业 ATS 或多人协作平台；
- 无边界网页抓取器；
- 用聊天历史或模型记忆替代业务数据库的通用助手；
- OpenCLI 本体。OpenCLI 是外部应用，CareerConsole 只通过受控 CLI 和本地插件调用。

## 3. 不可破坏的业务规则

1. **Agent 只输出受 Schema 约束的结构化结果。** 事实和业务状态候选必须由确定性 Domain 和 Application Service 落地；只读职业诊断经证据校验后可自动发布，但不得修改正式业务状态。
2. **个人档案是权威求职事实源。** Agent 整理或修改结果通过确定性结构、来源、敏感信息、重复和事实边界校验后直接以 `confirmed` 写入；简历生成不再等待用户逐条确认档案。
3. **推荐池与申请池分离。** 推荐被用户接受后才能建立待投递申请。
4. **申请绑定具体简历版本。** 确认投递时冻结岗位、简历和导出物快照。
5. **历史不可被未来覆盖。** 后续修改简历或岗位不能改变已投递申请的冻结材料。
6. **面试准备读取实际投递材料。** 没有已提交快照时不得生成正式准备包。
7. **邮件只是证据来源。** 高可信、低歧义招聘邮件可按确定性策略自动补录；其他情况进入待确认。
8. **邮箱同步只读。** 扫描已读和未读邮件，不执行 STORE、MOVE、DELETE、EXPUNGE 或发送邮件。
9. **主动邮件扫描最多一个月。** 招聘来源、邮件扫描、Scheduler、任务和面试等业务时间按 `Asia/Shanghai` 判断；普通界面时区由用户在设置中选择。
10. **工作区由用户选择。** Bootstrap 只保存当前工作区位置和最小启动元数据。
11. **不迁移旧 Career Store。** 新 CareerConsole 数据从当前业务模型开始建立。
12. **密钥不进入普通配置、文档、日志、API 响应或默认导出。**

## 6. 使用流程

### 6.1 首次启动

```powershell
.\career-console.cmd
```

打开 `http://127.0.0.1:8765`。首次进入 Bootstrap：

1. 选择父目录，系统在其下创建 `CareerConsole` 工作区。
2. 配置至少一个模型 Provider，并执行连接测试。
3. 按需配置 OpenCLI/牛客、BOSS、只读邮箱、QQ 和自动任务。
4. 完成向导并等待服务重启进入 Product 模式。

除工作区外，其余配置可跳过并稍后在“设置”完成。未配置的外部能力只会显示不可用或跳过，不应阻断基础手动流程。

### 6.2 建立和维护个人档案

1. 进入“个人资料 > 个人档案”，选择“导入资料”，上传简历或粘贴经历文本。
2. 专职 `profile_fact_extraction` Skill 清理排版/OCR 噪声、合并零散表述，并输出完整、规范化的业务对象。
3. 确定性应用服务校验结构、来源证据、联系方式、重复项、空值和事实边界；通过后直接以 `confirmed` 写入个人档案。
4. 导入不会创建个人档案 `ReviewTask` 或 `ReviewBundle`，也不会跳转到“待我处理”。
5. 若某条档案有误，在该条目中展开“修改”，输入修改指示；`profile_fact_revision` Skill 生成结构化修改结果，确定性校验通过后应用。
6. 对历史导入记录点击“重新整理档案”，系统使用当前 V3 Skill 重新处理原文；成功后替换仅由该文档支持的旧事实，保留手工事实和仍有其他文档依据的事实。
7. 导入、重整和修改都保留 `AgentRun`、来源证据、`FactRevision` 和 `ProfileChangeEvent`，供追溯与影响分析。

联系方式等敏感字段不得作为普通档案事实持久化。修改不得改变条目类别、引入无来源事实或把用户指示直接当作事实。旧版 `candidate_fact.v1` 的碎片候选和个人档案确认任务不属于当前正式路径；历史审查详情只为兼容保留，不显示在当前“待我处理”队列。
旧文档重整是显式受控操作，不通过重复上传隐式触发。只有 V3 提取和确定性校验全部成功后才替换旧内容；失败不得把已解析文档改成失败状态，也不得删除现有事实。未启用或无法解析 `fact_extraction` 任务时，导入或重整必须明确失败并提示用户前往“设置 > AI 服务”处理，不得静默切换到本地规则提取器。

“个人档案”和“洞察建议”不是两套互相替代的数据：

- 个人档案是正式业务的基础数据。V3 Agent 将简历原文整理为基础信息、教育、工作、项目、技能等完整对象：`content` 是供后续任务读取的规范化正文，允许清理混乱格式、合并片段和改善表达；`evidenceTexts` 单独保留可核验的原文证据。整理不得新增角色、技术、日期、数字、成果或个人贡献，也不得把“参与”增强为“负责/主导”。通过确定性校验并写入 `confirmed` 后，岗位匹配、简历生成和申请材料才会读取这些事实。
- 洞察建议是自动的二次分析。它只读取已确认个人档案、已保存求职偏好、正式申请变化和已确认面试改进项，并按 `interview`、`application`、`resume`、`learning`、`career_direction` 分类。不同分类分别关注面试表现、投递行为、简历表达与证据、学习缺口、长期方向与约束；缺少可信依据的分类可以不输出。
- 每条洞察只向用户展示“分析”和“建议”。不展示“分析依据”、证据 ID 或 AgentRun 跳转；证据引用继续保留在后端，用于确定性校验、权限检查和审计。不再维护独立的当前优势、优先级、本周策略、通用下一步或活动统计区块。
- “分析”和“建议”必须以简洁的简体中文输出，允许保留必要的英文技术名词；不符合语言策略的 Agent 结果会触发一次受控修复，仍不符合则整轮失败并保留上一轮有效建议。
- 诊断结果通过结构、证据 ID 和权限校验后直接以 `active` 发布，只供用户查看；“洞察建议”页面不提供手动生成、逐条确认、采用、拒绝或局部智能记录跳转，也不进入“待我处理”或创建 `ReviewTask`。诊断不得覆盖事实、修改申请状态或把建议写成已发生事件。
- 用户可在“设置 > 自动任务”选择每 1、3、7 或 14 天检查一次，默认 3 天，时间按中国时区判断。可信输入没有变化时复用当前结果；输入变化且重新分析成功时，新一组建议整体替换旧的当前建议，历史记录仅用于审计。
- 没有诊断时，岗位匹配和材料生成仍应直接使用已确认事实运行。数据库表名 `profile_insight_proposals` 是历史命名，不代表当前结果仍需审查。

### 6.3 获取机会和具体岗位

自动或手动运行牛客同步后：

1. 在“岗位推荐”查看招聘机会和每日具体岗位推荐。
2. 对招聘机会选择关注或忽略。
3. 获取完整 JD 后，在“目标岗位”通过文本、文件或 URL 建立具体岗位。
4. 运行岗位匹配，核对优势、硬性条件、缺口和行动建议。

招聘项目、校招批次或汇总页只是 `RecruitmentOpportunity`，不能代替 `JobPost`。

### 6.4 维护简历与生成岗位申请材料

可复用简历与岗位专用简历是两个作用域明确的资产流程。两者都以权威个人档案为事实来源，经 Agent 生成并通过确定性 Reviewer 校验后直接发布，不需要用户确认候选。

维护可复用简历：

1. 进入“我的简历 > 简历库”查看所有未归档的可复用简历。
2. 填写简历名称和生成要求，由 `standalone_resume_drafting` Agent 读取当前权威个人档案并生成结构化内容。
3. 确定性 Reviewer 校验事实引用、结构和风险；通过后直接创建正式简历及首个精确版本，不产生待确认任务。
4. 也可直接导入已有 DOCX/PDF/Markdown/文本简历并纳入简历库。
5. 使用星标设置一个默认简历。新申请需要预选简历时使用该默认项，但实际绑定始终记录具体 `resume_version_id`。
6. 每份简历可下载 DOCX，并可预览或下载 PDF。DOCX 是正式主格式，PDF 是兼容预览和辅助下载格式。
7. 不再使用的简历执行归档。已被申请或冻结快照引用的历史版本继续保留，不做破坏性物理删除。

生成和绑定岗位专用简历：

1. 打开申请详情，在当前岗位上下文中准备简历。
2. 可以从简历库选择一个精确版本并绑定；默认简历只是初始推荐，不替代用户对当前申请的明确选择。
3. 也可以填写岗位简历名称和生成要求。`material_drafting` Agent 结合权威个人档案、当前岗位要求及可选的简历库来源版本生成岗位专用简历。
4. 确定性 Reviewer 校验通过后，岗位专用简历直接创建为 `application` 作用域资产，并将返回的精确版本绑定到当前申请，`source` 记录为 `generated`。
5. 岗位专用简历不会自动进入简历库。用户需要复用时，可在“我的简历 > 投递岗位简历”中另存并命名为新的简历库资产。
6. 岗位专用简历可下载 DOCX，并可预览或下载 PDF；不能从简历库式入口单独删除。
7. 当申请被拒绝、获得 Offer、归档，或用户删除该申请时，其岗位专用简历随申请退休，不再作为活动资产展示。

旧版 `StandaloneResumeProposal`、`MaterialAgentProposal`、候选确认、编辑后复核和手动定稿流程属于遗留概念，不是当前正式用户路径。数据库或兼容代码中仍存在的旧对象不得被前端重新暴露为待确认流程。

### 6.5 建立并确认申请

推荐池和申请池严格分离：

1. 接受推荐或从具体岗位手动建立申请。
2. 从简历库选择精确版本，或为该岗位生成并绑定岗位专用简历。
3. 绑定成功后申请进入可投递准备状态，但系统不会自动投递。
4. 用户在外部招聘网站完成真实投递。
5. 回到 CareerConsole 执行独立、显式的“确认已投递”操作。
6. 系统冻结岗位版本、精确简历版本和导出物快照，优先保存 DOCX，并写入 `application_submitted` 事件。
7. 后续状态通过人工事件或邮件候选继续推进。

已有申请的岗位入口应进入“查看申请”，不能重复创建同一申请。

### 6.6 同步招聘邮件

1. 在“设置”添加 IMAP 账户并测试。
2. 在“招聘邮件”主动同步，或启用 Scheduler。
3. 系统读取已读和未读邮件；首次或主动回看最长 30 天。
4. 对求职相关邮件运行 `mail_intelligence` Skill。
5. 高可信、低歧义结果按确定性策略补录；冲突、缺少默认简历或不确定结果进入“待我处理”。
6. 用户确认后，申请事件、日程和待办才成为正式业务数据。

邮件正文属于不可信外部输入。邮件中的指令不能改变 Agent 权限，也不能直接修改业务状态。

### 6.7 面试准备与复盘

1. 申请出现面试事件后建立 Interview。
2. 系统从已投递申请的冻结岗位和材料生成准备包。
3. 用户记录时间变化、面试问题、回答和感受。
4. Agent 输出反馈和成长项候选。
5. 用户确认后，成长项才能进入后续策略和准备上下文。

面试纪要当前仍由用户手工维护；自动获取或录音转写尚未提供。待确认的面试反馈不会进入持续职业诊断。若申请没有冻结快照，系统应明确阻止正式面试准备，而不是退回读取最新简历。

### 6.8 每日工作方式

建议每天从“今日”开始：

1. 处理“待我处理”；
2. 查看今日任务、截止日期和面试安排；
3. 查看新增机会与具体岗位推荐；
4. 为值得投入的岗位完成匹配和材料；
5. 外部投递后回系统确认并冻结；
6. 同步招聘邮件并核对进度建议；
7. 记录面试结果和下一步行动。

## 8. Agent 与确定性业务边界

CareerConsole 保留 AgentLoop、Tools、Channels 和 Cron/Scheduler 作为可重构基础能力，但正式 Career 任务使用版本化 Task Definition 和 Skill。

当前任务注册包括：

- `profile_fact_extraction`
- `profile_fact_revision`
- `mail_intelligence`
- `profile_insight`
- `job_fit`
- `resume_direction`
- `standalone_resume_drafting`
- `material_drafting`
- `material_review`
- `daily_job_recommendation`
- `interview_preparation`
- `interview_reflection`
- `daily_digest`

个人档案采用自动维护路径：

```text
导入资料或用户对具体档案提出修改指示
→ profile_fact_extraction / profile_fact_revision 在固定 Schema 和无工具权限下运行
→ 确定性服务校验结构、来源、敏感信息、重复、版本和事实边界
→ 保存 AgentRun、来源证据、修订和变化事件
→ 通过后直接写入或更新 confirmed 档案
→ 不创建 ReviewTask / ReviewBundle
```

申请、邮件和面试等有歧义的正式业务变化继续采用人工裁决路径：

```text
确定性服务准备最小上下文
→ Task Agent 在固定 Schema 和权限下运行
→ 校验结构、引用和敏感信息
→ 保存 AgentRun 与 Proposal
→ ReviewTask/ReviewBundle 等待用户决定
→ 确定性应用服务写入正式状态
```

持续职业诊断采用独立的只读发布路径：

```text
确定性服务准备已确认事实、偏好、正式申请变化和已确认面试改进项
→ profile_insight Task Agent 在无工具权限下运行
→ 按面试、投递、简历、学习、职业方向输出分析和建议
→ 校验 Schema、证据 ID 和输入边界
→ 保存 AgentRun，并在成功后用新结果替换当前 active ProfileInsight
→ 不创建 ReviewTask，不修改正式事实或申请状态
```

简历生成采用直接发布路径：

```text
确定性服务准备权威个人档案、用户生成要求，以及岗位专用场景下的当前 JD
→ standalone_resume_drafting / material_drafting Task Agent 在受控权限和固定 Schema 下运行
→ 确定性 Reviewer 校验结构、事实引用、岗位引用和风险
→ 通过后直接创建 Resume、ResumeVersion 与 DOCX/PDF 导出物
→ 简历库生成进入 library 作用域；岗位生成进入 application 作用域并绑定当前申请
→ 不创建候选确认任务，不自动提交申请
```

后台任务不得默认获得通用命令执行、任意文件访问或外部写操作权限。外部网页、JD 和邮件一律按不可信数据处理。

## 9. 自动任务

Scheduler 是公共运行底座，不是一个同时控制所有业务的统一开关。设置页中的自动任务必须分别保存和执行：

- “洞察建议”开关只控制洞察自动刷新；用户可选择 1、3、7 或 14 天周期和执行时间，默认每 3 天；
- “任务与日程提醒”开关只控制到期 Schedule 和 Reminder 检查；
- “牛客招聘同步”开关只控制牛客自动同步，具体执行时间使用牛客数据源配置；
- “招聘邮箱扫描”开关只控制 IMAP 只读同步和后续邮件分析，扫描频率使用邮箱数据源配置；
- “外部通知发送”开关只控制向已启用渠道分发通知；
- 后台调度服务总开关和轮询秒数属于高级运行参数。关闭底座会暂停所有自动任务，但各业务开关仍保持独立配置。

BOSS 当前只支持用户手动运行，不进入自动 Scheduler。牛客每日自动获取按中国时区当天范围执行，7、14、30 天历史回填必须由用户主动触发。档案变化引起的岗位或材料影响任务按其业务事件独立处理，不由洞察周期控制。所有自动任务均记录脱敏的 SchedulerRun 历史；单项失败应隔离记录并继续其他已启用任务，不能让一个来源破坏整体 readiness。

## 10. 配置与密钥

普通配置位于：

```text
<workspace>/config/application.json
```

配置采用强类型 Schema、revision 和乐观并发控制。前端“设置”是普通用户的统一配置入口，支持保存、检查和独立连接测试。

`general.timezone` 是普通界面显示偏好，当前提供常见 IANA 时区。招聘来源的每日范围、邮件主动扫描、Scheduler、任务提醒和面试业务时间继续固定按 `Asia/Shanghai` 判断，不能通过修改界面时区改变这些业务边界。

敏感值遵守以下规则：

- API key、token、邮箱授权码和 QQ 凭据不写入普通配置；
- 普通读取 API 只返回 masked metadata 或 secret reference；
- 日志和运行审计不得记录明文；
- 默认导出不包含凭据；
- 可选凭据 Vault 使用口令加密；
- 无安全凭据后端时应 fail closed，不能降级为明文文件。

## 11. 工作区和数据

工作区结构：

```text
<父目录>/CareerConsole/
├── workspace.json

├── data/career-console.sqlite3
├── secrets/
├── blobs/
├── exports/

```

Windows Bootstrap 只保存当前工作区路径、workspace ID 和更新时间。业务数据库、文件、日志和密钥不进入 Bootstrap。

工作区支持：

- 创建与切换前验证；
- SQLite `quick_check` 和写入探针；
- 带 manifest 和 SHA-256 的迁移包；
- 可选加密凭据 Vault；
- 备份、导出、垃圾回收和删除。

不要手工复制正在运行的 SQLite 主文件、WAL 和 SHM。使用产品备份或工作区迁移能力。

## 12. 安全与隐私

- HTTP 默认只绑定 `127.0.0.1`、`localhost` 或 `::1`。
- 浏览器先交换本地 session，写请求校验 CSRF 和 Origin。
- 外部 HTML 和邮件按不可信内容处理。
- 文件上传限制类型和大小，不执行文档中的宏或脚本。
- 邮箱连接器只读。
- 日志对 token、password、cookie、authorization、邮箱和正文做脱敏。
- Agent 上下文遵循最小必要原则。
- 申请冻结材料和用户确认事实默认长期保留；临时导出、运行 trace 和日志按配置保留。

## 13. 技术结构

CareerConsole 是模块化单体：

```text
interfaces ─┐
            ├─> application ─> domain
infrastructure ┘

runtime = 通用 Agent 内核，由 infrastructure 适配
```

- Backend：Python 3.11+、FastAPI、SQLAlchemy 2、Alembic、SQLite WAL。
- Frontend：React 19、TypeScript、TanStack Query、Vite。
- Job：SQLite 持久后台任务，不依赖 Redis/Celery。
- Agent：专职 Skill、固定输入输出 Schema、AgentRun 审计。
- External：OpenCLI、IMAP、Provider 和 QQ 通过受控 Adapter 接入。

业务代码依赖方向不得倒置。Domain 不依赖 FastAPI、SQLAlchemy、OpenCLI 或模型 SDK。

## 17. 文档维护协议

本仓库只持续维护本文，不再按产品、架构、功能、运维和用户手册拆分多套重复文档。

每个功能变更必须同步检查：

1. 产品定位或非目标是否变化；
2. 不可破坏的业务规则是否变化；
3. 核心业务对象或生命周期是否变化；
4. 功能总表的状态、能力和边界是否变化；
5. 用户实际操作步骤和页面入口是否变化；
6. Agent Task、Scheduler、Connector 或配置是否变化；
7. 工作区、安全、隐私或密钥规则是否变化；
8. CLI、启动、测试和诊断命令是否变化；
9. 已知缺口是否已经完成或出现新缺口；
10. 数据库 head revision 和文档基线日期是否需要更新。

维护要求：

- 一次功能变更只在本文维护一份完整事实，不新建重复专题文档；
- 临时分析、测试报告和交接记录放在任务上下文或 `.runtime`，不进入持久文档；
- 必须区分当前实现和未来计划；
- 删除功能时同步删除本文对应描述；
- 新增页面或正式 API 时补充到相应业务区域；
- 任何示例不得包含真实密钥、Cookie、Token、邮箱授权码或个人敏感正文。

## 18. 当前基线结论

CareerConsole 已具备从权威个人档案、岗位发现、具体 JD、匹配推荐、可复用简历库、岗位专用简历生成与精确绑定，到显式投递冻结、邮件跟进、任务、手工面试纪要和持续职业诊断的本地业务闭环。简历以 DOCX 为主交付、PDF 为辅助预览，生成后直接成为正式资产但绝不自动提交申请。当前主要交付缺口集中在最终 Windows 产品化安装和 Launcher，而不是核心业务对象缺失。

产品继续演进时，应优先完善真实用户流程中的阻塞和不合理点，并保持三条主线稳定：Agent 输出受约束的结构化结果、确定性服务维护正式状态、所有关键历史可追溯且不可被未来修改。自动职业诊断只能作为只读建议发布，不能成为绕过正式业务规则的写入通道。
