# 2. 当前项目背景

当前项目是在 nanobot 基础上进行过简单求职方向改造的版本。

现有改造仍然比较初步，可能只实现了部分候选人信息、简历管理或求职相关工具，并没有形成一个完整的求职产品。

当前版本存在的主要问题包括：

* 仍然以通用 Agent 为主要定位。
* 求职功能可能只是通用 Agent 上附加的若干工具。
* 用户资料、岗位、申请、邮件、面试等信息缺少统一的数据模型。
* 缺少完整的求职业务闭环。
* 缺少清晰的业务分层。
* Agent 推理与确定性业务逻辑之间的边界不明确。
* 缺少持续运行的信息同步能力。
* 缺少完善的本地 Web 操作界面。
* 缺少申请时间线、材料版本和面试反馈的长期沉淀。
* 原 nanobot 中可能保留了大量与求职产品无关的功能。

后续我们不再把该项目定位为通用 Agent。

新的方向是：

> 将当前修改版 nanobot 彻底改造成一个专门服务于个人求职全过程的本地求职 Agent。

因此，原 nanobot 中与该目标无关的功能可以在完成分析后逐步删除、简化或替换。

但是本阶段不要直接删除代码。

首先需要对所有主要模块进行评估，并分别标记为：

```text
保留
复用
重构
替换
迁移
删除
待确认
```

# 3. 目标产品定位

目标产品是：

> 一个本地优先、持续运行、面向个人完整求职周期的智能求职 Agent。

它运行在用户自己的电脑上。

系统通过本地 Web 页面为用户提供操作界面，通过 Agent、定时任务和各种 Connector 持续处理用户的求职信息。

它不是一次性问答工具，而是长期维护用户求职上下文的个人求职系统。

产品需要长期知道：

* 用户具备哪些真实经历和能力。
* 用户想找什么类型的岗位。
* 用户已经发现了哪些岗位。
* 用户申请了哪些公司和岗位。
* 每次申请使用了哪一版材料。
* 当前每个申请进行到哪个阶段。
* 用户接下来有什么笔试、测评和面试。
* 用户过去面试中出现过哪些问题。
* 用户应该优先改进哪些能力。
* 哪些岗位、材料和投递渠道对用户更有效。

# 4. 核心产品原则

## 4.1 本地优先

用户的敏感信息默认保存在本地，包括：

* 简历。
* 教育和工作经历。
* 邮件。
* 申请记录。
* 面试录音。
* 面试反馈。
* Offer 信息。
* 求职偏好。
* 模型调用产生的分析结果。

云端模型可以作为可选推理服务，但业务数据和长期状态默认由本地系统管理。

## 4.2 持续运行

系统不是只在用户主动对话时工作。

它需要能够通过定时任务或事件触发持续执行：

* 同步新邮件。
* 检查新的招聘信息。
* 检查临近截止的岗位。
* 检查即将进行的笔试和面试。
* 检查长时间无响应的申请。
* 生成待办、提醒和准备建议。

## 4.3 确定性业务优先

以下内容不应完全交给大模型自由决定：

* 申请状态。
* 时间和提醒。
* 数据关联关系。
* 材料版本。
* 状态转换规则。
* 事件时间线。
* 用户确认结果。
* 数据持久化。

这些内容应该由明确的业务代码和数据模型管理。

Agent 主要负责：

* 非结构化信息理解。
* 分类。
* 信息提取。
* 匹配分析。
* 内容生成。
* 审查。
* 总结。
* 复杂任务规划。

## 4.4 所有关键操作可追溯

系统中的重要变化应该记录：

* 变化发生的时间。
* 变化前后的内容。
* 信息来源。
* Agent 判断结果。
* 判断置信度。
* 是否经过用户确认。
* 对应的原始邮件、文章、文件或页面。

## 4.5 Agent 受控执行

Agent 不应直接任意操作数据库。

Agent 应通过清晰的业务工具完成操作，例如：

```text
create_job_candidate
evaluate_job
create_application
propose_application_event
confirm_application_event
create_resume_draft
save_interview_feedback
create_reminder
```

## 4.6 用户事实不能被虚构

简历、求职信、自我介绍和面试回答只能引用用户已经确认的事实。

AI 可以重新组织和优化表达，但不能创造不存在的：

* 经历。
* 项目。
* 技能。
* 成果。
* 数据指标。
* 职位。
* 奖项。

# 5. 目标用户

第一阶段主要服务：

* 校招学生。
* 应届毕业生。
* 秋招和春招求职者。
* 同时投递大量公司的用户。
* 需要管理多个笔试和面试安排的用户。
* 重视个人数据隐私的用户。
* 希望使用 AI 优化简历和面试表现的用户。

第一阶段暂不重点考虑：

* 企业招聘方。
* 猎头。
* HR 团队。
* 多人协作。
* 多租户 SaaS。
* 企业级招聘管理。
* 自动批量投递。

# 6. 产品需要解决的核心问题

## 6.1 用户信息不完整且分散

用户的能力和经历分散在：

* 基础简历。
* 不同版本简历。
* 项目文档。
* GitHub 项目。
* 成绩单。
* 证书。
* 面试记录。
* 用户自己补充的描述。

系统需要将这些信息维护成统一的用户事实库。

## 6.2 招聘信息来源分散

招聘信息可能来自：

* 学校就业公众号。
* 学院公众号。
* 企业招聘公众号。
* 招聘邮件。
* 企业招聘官网。
* 学校就业网站。
* 微信群。
* PDF 招聘公告。
* 浏览器中的岗位页面。
* RSS。
* 用户主动粘贴或上传的内容。
* 未来可以稳定接入的其他来源。

系统需要将这些来源统一接入并转化为结构化岗位或招聘活动。

## 6.3 申请进度容易混乱

用户通常难以长期维护：

* 是否已经投递。
* 使用了哪份简历。
* 是否收到网申确认。
* 是否需要完成测评。
* 笔试时间。
* 面试轮次。
* 面试时间变化。
* 是否收到拒信。
* 是否收到 Offer。

系统需要通过用户操作和邮件同步自动维护完整进度。

## 6.4 求职材料缺少针对性

系统需要根据不同岗位：

* 分析岗位要求。
* 找出用户最相关的经历。
* 调整简历重点。
* 优化项目描述。
* 生成求职信。
* 生成自我介绍。
* 审查材料是否真实、完整和适合岗位。

## 6.5 面试经验没有沉淀

用户每次面试后通常没有形成长期数据。

系统需要沉淀：

* 面试问题。
* 用户回答。
* 用户自我评价。
* 面试官反馈。
* 失败原因。
* 薄弱知识点。
* 表达问题。
* 后续改进计划。

这些信息需要用于下一次面试准备。

# 7. 产品核心业务闭环

目标产品的核心业务闭环如下：

```text
建立用户事实库
        ↓
接入用户的信息来源
        ↓
持续发现新的招聘信息
        ↓
识别公司、岗位和招聘活动
        ↓
根据用户信息判断是否适合
        ↓
提醒用户并生成行动计划
        ↓
生成和审查申请材料
        ↓
记录用户完成投递
        ↓
持续同步用户邮件
        ↓
维护各公司和岗位的申请状态
        ↓
提醒笔试、测评和面试时间
        ↓
生成针对性的准备建议
        ↓
记录笔试和面试反馈
        ↓
分析用户表现和薄弱环节
        ↓
更新用户求职策略和准备重点
```

后续所有模块都应围绕这个闭环设计。

# 8. 核心功能模块

## 8.1 用户事实库

该模块参考 `ai-job-search` 的候选人资料管理思路，但目标是将信息进一步结构化。

需要维护：

* 基本信息。
* 联系方式。
* 教育经历。
* 实习经历。
* 工作经历。
* 项目经历。
* 技术技能。
* 软技能。
* 证书。
* 比赛和奖项。
* 作品链接。
* GitHub 仓库。
* 可量化成果。
* STAR 案例。
* 目标岗位。
* 目标行业。
* 目标城市。
* 求职时间范围。
* 工作方式偏好。
* 不接受的条件。
* 每条事实的来源。
* 每条事实是否已经确认。

需要支持：

* 从现有简历导入。
* 从 PDF、DOCX、Markdown 或纯文本解析。
* 用户手动补充和修改。
* Agent 提出补全建议。
* 用户确认后写入事实库。
* 事实版本和变更记录。

---

## 8.2 简历和申请材料工作台

该模块重点吸收 `ai-job-search` 的以下思路：

* 单一事实来源。
* 针对岗位定制材料。
* Drafter–Reviewer 工作流。
* 每次申请保存材料快照。
* 输出文件验证。
* 不允许虚构经历。

计划功能包括：

* 基础简历管理。
* 多版本简历管理。
* 岗位定制简历。
* 求职信生成。
* 自我介绍生成。
* 项目描述优化。
* 岗位关键词覆盖分析。
* 事实一致性检查。
* ATS 可读性检查。
* PDF 或 DOCX 导出。
* 材料版本与申请记录绑定。

推荐工作流：

```text
读取岗位要求
→ 查询用户事实库
→ 选择相关经历
→ Drafter 生成材料草稿
→ Reviewer 审查
→ 根据审查结果修改
→ 用户确认
→ 保存最终版本
→ 与对应申请绑定
```

---

## 8.3 招聘信息源管理

系统允许用户配置自己的招聘信息来源。

信息源需要抽象成统一的 Connector，而不是把所有逻辑写死在公众号上。

可能的信息源包括：

* 公众号文章。
* 学校就业网站。
* RSS。
* 招聘邮件订阅。
* 企业招聘官网。
* 浏览器页面。
* 本地文件夹。
* PDF 或截图。
* 用户主动转发的消息。
* 公开 API。
* 未来可以稳定接入的其他来源。

每个信息源需要维护：

* 来源类型。
* 来源名称。
* 访问方式。
* 同步频率。
* 上次同步时间。
* 增量游标。
* 当前状态。
* 最近错误。
* 用户授权信息。
* 数据可信度。

统一流程应为：

```text
Connector 获取新内容
→ 去重
→ 判断是否为招聘信息
→ 提取公司和招聘活动
→ 提取岗位
→ 保存原始内容
→ 与用户事实库进行匹配
→ 创建岗位候选或提醒
```

---

## 8.4 公众号和类似信息源联动

公众号是重要示例，但不是唯一信息来源。

目标能力是：

* 用户提供需要关注的就业公众号或其他稳定来源。
* 系统检测到来源更新。
* 获取新增文章。
* 判断文章是否与招聘相关。
* 提取公司、岗位、地点、招聘对象和截止时间。
* 判断是否存在适合用户的岗位。
* 生成匹配分析。
* 立即提醒用户。
* 根据截止时间生成投递计划。
* 为高优先级岗位生成准备任务。

需要重点分析现实可行性：

* 是否存在稳定接口。
* 是否必须依赖用户本地登录状态。
* 是否只能通过浏览器扩展或主动转发实现。
* 是否可以从微信本地环境获取。
* 哪些方案适合 Demo。
* 哪些方案适合长期实现。
* 哪些方案风险过高，不应成为核心依赖。

Codex 不应假设公众号可以被稳定自动抓取。

需要在报告中区分：

```text
第一阶段可实现方案
中期可实现方案
实验性方案
不建议依赖的方案
```

## 8.5 岗位池和岗位分析

系统需要维护统一岗位池。

岗位来源可能是：

* 信息源自动发现。
* 邮件提取。
* 浏览器导入。
* 用户粘贴。
* 文件导入。
* 用户手动创建。

岗位需要包含：

* 公司。
* 岗位名称。
* 岗位描述。
* 岗位要求。
* 地点。
* 类型。
* 招聘对象。
* 截止时间。
* 信息来源。
* 原始内容。
* 首次发现时间。
* 最后更新时间。
* 匹配分析。
* 当前处理状态。

系统需要进行：

* 公司名称归一化。
* 岗位名称归一化。
* 重复岗位检测。
* 岗位要求结构化。
* 硬性条件检查。
* 用户能力匹配。
* 优势和缺口分析。
* 是否建议申请。
* 申请优先级判断。
* 截止时间和准备成本分析。

岗位分析不应只输出一个无法解释的分数。

每个判断应尽可能关联：

* 具体岗位要求。
* 用户事实库中的具体证据。
* 当前无法满足的要求。
* 结论置信度。

## 8.6 申请进度管理

系统需要为每个公司和岗位建立独立申请记录。

建议状态包括：

```text
发现
待评估
建议申请
暂不申请
准备材料
待投递
已投递
网申确认
测评
笔试
面试
Offer
拒绝
主动结束
归档
```

申请不能只保存一个当前状态。

必须保存完整事件时间线，例如：

```text
2026-08-01 从学校公众号发现岗位
2026-08-02 完成岗位匹配分析
2026-08-03 生成简历版本 V4
2026-08-04 用户确认完成投递
2026-08-05 收到网申确认邮件
2026-08-10 收到笔试通知
2026-08-12 完成笔试
2026-08-18 收到一面邀请
```

每个申请事件需要包含：

* 事件类型。
* 发生时间。
* 创建时间。
* 来源。
* 原始证据。
* Agent 置信度。
* 是否经过用户确认。
* 前一状态。
* 后一状态。
* 关联邮件或文件。

---

## 8.7 邮件同步与进度维护

邮件联动是目标产品的核心差异化能力之一。

系统需要在本地连接用户邮箱，并持续增量读取新邮件。

需要识别的邮件类型包括：

* 网申确认。
* 测评邀请。
* 笔试通知。
* 面试邀请。
* 面试时间调整。
* 面试通过通知。
* 拒信。
* Offer。
* 入职通知。
* 招聘活动。
* 宣讲会。
* 无关邮件。
* 无法判断。

推荐处理流程：

```text
同步新邮件
→ 保存必要元数据
→ 规则初筛
→ 判断是否与招聘相关
→ 提取公司、岗位、事件和时间
→ 匹配已有岗位或申请
→ 生成状态变更建议
→ 创建提醒和准备任务
→ 用户确认或按规则自动处理
→ 写入申请时间线
```

需要重点探索：

* nanobot 当前 Email Channel 的实现方式。
* 是否支持 IMAP。
* 是否支持增量同步。
* 是否保存邮件 UID 或游标。
* 是否适合直接复用。
* Email Channel 是通信通道，还是可以扩展为数据 Connector。
* 是否应该新建独立 Email Connector。
* 如何处理 Gmail、Outlook、QQ 邮箱和 163 邮箱。
* 如何安全保存凭证。
* 如何避免把全部无关邮件传给模型。
* 如何处理邮件附件。
* 如何处理邮件线程。
* 如何将同一封邮件与正确申请匹配。

重要状态变更初期默认需要用户确认。

---

## 8.8 时间、提醒和准备任务

系统需要根据岗位、邮件和申请事件维护时间。

主要时间类型包括：

* 岗位截止时间。
* 测评截止时间。
* 笔试时间。
* 面试时间。
* 面试调整时间。
* 宣讲会时间。
* Offer 确认时间。
* 用户计划的投递时间。
* 跟进时间。

系统需要支持：

* 提前若干小时或若干天提醒。
* 多阶段提醒。
* 时间冲突检测。
* 过期任务检测。
* 用户确认完成。
* 自动生成准备任务。
* 每日或每周求职简报。

例如收到笔试通知后，系统可以自动生成：


# 15. Demo 范围建议

本阶段需求分析需要提出一个现实可行的 Demo。

初步建议 Demo 闭环是：

1. 用户导入一份简历。

3. 用户粘贴或上传一个岗位。
4. 系统提取岗位要求。
5. 系统分析岗位与用户的匹配情况。
6. 系统生成定制简历草稿。
7. Reviewer 对简历进行审查。
8. 用户确认投递，并创建申请记录。
9. 系统连接邮箱并增量读取招聘邮件。
10. 系统识别面试、笔试或拒信。
11. 系统提出申请状态更新建议。
12. 系统创建时间提醒和准备任务。
13. 用户手动填写或上传面试反馈。
14. 系统分析面试反馈并生成改进建议。
15. 用户可以在本地 Web 页面查看岗位、申请、邮件和时间线。

* 用户粘贴文章正文。
* 用户粘贴文章链接。

* 系统分析文章中的岗位是否适合用户。

* 自动遍历用户全部公众号。

* 实时面试录音。

# 17. 项目规范要求

请在需求分析报告中提出适合当前项目的规范。

至少覆盖以下内容。

## 17.1 模块边界

明确：

* Domain 不依赖 Agent。
* Agent 通过业务接口访问 Domain。
* Connector 不直接修改业务状态。
* Web API 不直接包含复杂业务逻辑。
* 数据库访问集中在 Repository 或 Store 层。

## 17.2 数据规范

要求：

* 所有时间明确时区。
* 所有外部实体保存原始来源 ID。
* 所有同步操作支持幂等。
* 所有状态变化保存事件。
* 所有 AI 判断保存置信度和证据。
* 所有用户事实保存来源和确认状态。
* 所有材料保存版本。
* 所有重要操作可撤销或更正。

## 17.3 Agent 规范

要求：

* Agent 不直接执行任意 SQL。
* Agent 不任意修改文件。
* Agent 只能调用已注册工具。
* Tool 输入输出应使用结构化 Schema。
* 高风险操作必须确认。
* Agent 输出应区分事实、推断和建议。
* 生成内容必须引用事实库。
* Agent Run 需要保存日志。

## 17.4 Connector 规范

要求：

* 每个 Connector 具有统一接口。
* 支持增量同步。
* 支持失败重试。
* 保存同步游标。
* 支持去重。
* 不直接写入 Application 状态。
* 将外部内容转成标准 Source Event。
* 连接器失效不能影响核心系统。

## 17.5 安全和隐私

需要分析：

* 邮箱凭证如何保存。
* OAuth Token 如何保存。
* Cookie 如何保存。
* 原始邮件是否全部落库。
* 无关邮件是否立即丢弃。
* 模型调用前如何进行数据最小化。
* 面试录音如何保存。
* 用户如何删除全部数据。
* 日志中如何避免暴露敏感内容。
* 浏览器扩展如何认证 localhost 服务。

## 17.6 测试规范

需要覆盖：

* Domain 单元测试。
* 状态机测试。
* Repository 测试。
* Connector 模拟测试。
* 邮件分类样例测试。

## 1. 招聘信息获取方案

招聘网站信息采用：

> OpenCLI + 浏览器登录状态 + 网站 Adapter + 本地定时任务

的方式获取。

OpenCLI 用于将登录后的网页能力转化为可调用的命令或浏览器操作接口。它可以通过 Browser Bridge 连接 Chrome 或 Chromium，复用用户已经登录的网站会话，并支持页面导航、DOM 内容读取、点击、输入、网络请求分析和结构化数据提取。

我们的系统不再以传统服务端爬虫作为主要招聘信息来源。

### 1.1 核心执行流程

```text
本地定时任务触发
        ↓
检查目标网站 Adapter 状态
        ↓
检查 OpenCLI 和浏览器连接状态
        ↓
按需启动或连接专用浏览器 Profile
        ↓
复用用户已保存的登录状态
        ↓
调用目标网站 Adapter
        ↓
获取最新招聘信息
        ↓
转换为统一数据结构
        ↓
与本地历史数据比较
        ↓
识别新增、更新、下线或重复岗位
        ↓
保存 Source Event 和岗位数据
        ↓
执行用户匹配分析
        ↓
生成提醒或待确认任务
        ↓
释放当前浏览器任务资源
```

初期默认每天扫描两次。

扫描频率应由配置管理，不能硬编码在具体 Adapter 中。

例如：

```yaml
job_sources:
  default_schedule:
    times:
      - "09:00"
      - "18:00"
```

浏览器不需要长期停留在目标招聘页面。

系统只在以下情况使用浏览器：

* 自动扫描。
* 首次登录。
* 登录状态失效后重新登录。
* Adapter 调试。
* 用户主动执行招聘信息刷新。
* 用户创建或验证自定义 Adapter。

需要由 Codex 分析 OpenCLI 的运行机制，判断实际实现中应采用：

* 完全按需启动浏览器；
* 连接已有 Chrome 实例；
* 保留轻量后台 Browser Bridge；
* 使用专用 Chrome Profile；

中的哪种组合。

产品层面的要求是：日常使用不要求用户一直手动打开招聘网站页面。

---

## 1.2 OpenCLI 在系统中的职责

OpenCLI 主要负责：

* 连接用户本地浏览器。
* 复用浏览器登录状态。
* 操作登录后的招聘网站。
* 读取结构化 DOM。
* 分析页面中的网络请求。
* 调用已有 Adapter。
* 为新网站生成或调试 Adapter。
* 输出 JSON、YAML、CSV 或其他结构化结果。
* 返回明确的执行状态和错误码。

OpenCLI 不负责：

* 用户职业档案管理。
* 岗位去重。
* 用户与岗位匹配。
* 申请状态管理。
* 数据库存储。
* 邮件同步。
* 提醒。
* 求职材料生成。
* 面试准备。

这些能力由 Career Domain 和 Agent 层负责。

---

## 1.3 Adapter 在系统中的职责

每个招聘网站通过独立 Adapter 接入系统。

Adapter 负责理解具体网站，包括：

* 登录状态判断。
* 搜索页结构。
* 列表页结构。
* 岗位详情页结构。
* 分页或加载更多逻辑。
* 网站内部接口。
* 字段映射。
* 页面变化适配。

Adapter 不应直接访问 Career Domain 数据库，也不应自行判断岗位是否适合用户。

Adapter 的输出必须转换为统一数据结构。

---

## 1.4 统一 Adapter 能力

项目层面定义统一 Adapter 接口。

初步要求如下：

```text
status
login
latest
detail
```

### `status`

用于检查：

* OpenCLI 是否可用。
* Browser Bridge 是否连接。
* 指定浏览器 Profile 是否存在。
* 目标网站是否可以访问。
* 用户是否处于登录状态。
* Adapter 是否能够正常解析页面。

建议返回：

```json
{
  "site": "site-a",
  "adapter_version": "1.0.0",
  "available": true,
  "browser_connected": true,
  "authenticated": true,
  "requires_login": false,
  "last_checked_at": "2026-07-22T10:00:00+08:00",
  "error_code": null,
  "message": null
}
```

### `login`

用于：

* 打开目标网站登录页面。
* 使用指定浏览器 Profile。
* 等待用户完成登录。
* 检查登录是否成功。
* 保存登录成功状态。

登录动作不应自动填写用户账号和密码，除非未来明确设计安全的凭证方案。

初期以用户人工完成登录为主。

### `latest`

用于获取一定时间范围或一定数量的最新招聘信息。

建议支持：

```text
since
limit
page
keyword
location
job_type
```

具体网站不支持的参数可以忽略，但 Adapter 应返回统一格式。

### `detail`

根据岗位的外部 ID 或 URL 获取完整岗位详情。

用于补充：

* 完整岗位描述。
* 岗位要求。
* 工作地点。
* 截止日期。
* 招聘对象。
* 申请入口。
* 公司信息。
* 页面更新时间。

---

## 1.5 Adapter 统一输出

所有网站 Adapter 最终输出统一的岗位候选结构。

示例：

```json
{
  "source_type": "opencli_adapter",
  "source_name": "site-a",
  "external_id": "job-123456",
  "source_url": "https://example.com/job/123456",
  "company_name": "示例公司",
  "job_title": "后端开发工程师",
  "location": "北京",
  "job_type": "campus",
  "employment_type": "full_time",
  "description": "原始岗位描述",
  "requirements": [
    "熟悉 Java",
    "熟悉数据库"
  ],
  "application_deadline": "2026-09-30T23:59:59+08:00",
  "published_at": "2026-07-22T08:00:00+08:00",
  "updated_at": "2026-07-22T08:00:00+08:00",
  "collected_at": "2026-07-22T09:00:00+08:00",
  "raw_payload": {},
  "adapter_version": "1.0.0"
}
```

需要保留：

* 外部 ID。
* 原始 URL。
* 原始数据。
* Adapter 版本。
* 抓取时间。
* 网站更新时间。

这样在 Adapter 更新、字段解析变化或数据出现异常时可以追溯。

---

## 1.6 Adapter 类型

Adapter 分为三类。

```text
内置 Adapter
用户自定义 Adapter
用户覆盖 Adapter
```

### 内置 Adapter

由项目仓库维护。

特点：

* 项目默认提供。
* 经过基本测试。
* 用户首次登录后即可使用。
* 随项目版本更新。
* 适用于一到两个重点招聘网站。
* 项目维护者负责适配常见页面变化。

### 用户自定义 Adapter

由用户创建，用于支持项目未内置的网站。

特点：

* 保存在用户数据目录。
* 不受项目更新影响。
* 可以由 OpenCLI Adapter Author Skill 辅助生成。
* 用户可以自行修改和测试。
* 不直接提交到主仓库也可以使用。

### 用户覆盖 Adapter

用于临时替换项目内置 Adapter。

适用场景：

* 内置 Adapter 暂时失效。
* 用户需要修改特定行为。
* 用户希望提前测试新版 Adapter。
* 用户使用的网站版本或地区页面不同。

加载优先级建议为：

```text
用户覆盖 Adapter
    ↓
用户自定义 Adapter
    ↓
项目内置 Adapter
```

具体加载规则需要避免同名自定义 Adapter 与内置 Adapter 产生不可预测冲突。

## 1.10 登录失效处理

每次扫描前，系统应检查登录状态。

出现以下情况时，应将来源标记为需要重新登录：

* Adapter 返回认证失败。
* OpenCLI 返回认证相关错误。
* 页面跳转到登录页。
* 关键登录用户元素消失。
* 网站返回未授权结果。
* Adapter 明确判断 Cookie 或会话已失效。

处理流程：

```text
检测到登录失效
    ↓
停止该来源本次扫描
    ↓
记录同步失败事件
    ↓
将来源状态改为 requires_login
    ↓
通知用户
    ↓
用户执行重新登录
    ↓
系统打开目标登录页
    ↓
检测登录成功
    ↓
恢复后续定时扫描
```

统一命令示例：

```bash
job-agent login site-a
```

Web 页面也应提供“重新登录”按钮。

登录失效只暂停对应来源，不应影响：

* 邮件同步。
* 其他招聘网站扫描。
* 本地岗位管理。
* 简历生成。
* 面试管理。

* 公司名称。
* 岗位名称。
* 地点。
* 描述哈希。

需要识别：

```text
跨来源转载岗位
```

Adapter 只负责返回网站数据。

增量判断和去重属于 Career Application 或 Domain 层。

建议保存每次来源同步运行记录：

```text

```

至少包含：

* 来源。
* 开始时间。
* 结束时间。
* 扫描数量。
* 新增数量。
* 更新数量。
* 重复数量。

## 1.12 招聘信息采集失败处理

需要区分不同失败类型：

```text
OpenCLI 未安装
Browser Bridge 未连接
浏览器 Profile 不存在
登录失效
Adapter 不存在
Adapter 解析失败
网站页面变化
网络超时
输出 Schema 不合法
网站暂时不可用
被限制访问
未知错误
```

不同错误应采用不同处理方式。

例如：

* 登录失效：提示用户登录。
* Adapter 解析失败：禁用当前 Adapter 并提示升级。
* 网络超时：自动重试。
* Schema 错误：记录原始输出，停止写入正式岗位表。
* 网站不可用：保留来源，下一周期重试。

不得因为单个来源失败而终止整个 Agent。

# 2. 邮箱读取方案

邮箱通过标准 IMAP 协议接入。

项目初期不依赖 Gmail 或 Outlook 专有 API，从而支持：

* 学校邮箱。
* 企业邮箱。
* QQ 邮箱。
* 163 邮箱。
* 支持 IMAP 的其他邮件系统。

邮箱模块初期只提供只读能力。

明确不提供：

* 发送邮件。
* 回复邮件。
* 删除邮件。
* 移动邮件。
* 标记已读。
* 修改标签。
* 修改邮件内容。

---

## 2.1 邮箱模块目标

邮箱模块主要用于：

* 发现用户历史上的求职申请。
* 识别新的求职进度通知。
* 提取笔试和面试时间。
* 提取待办事项。
* 维护公司和岗位的申请进度。
* 为提醒和面试准备提供触发条件。

邮箱模块不是一个完整邮件客户端。

---

## 2.2 邮箱配置

用户需要提供：

* 邮箱地址。
* IMAP 服务器地址。
* IMAP 端口。
* 是否启用 SSL/TLS。
* 用户名。
* 邮箱授权码或应用密码。
* 需要读取的邮箱文件夹。
* 首次同步时间范围。
* 后续同步频率。

示例配置：

```yaml
email:
  enabled: true
  address: "user@example.com"
  imap:
    host: "imap.example.com"
    port: 993
    ssl: true
    username: "user@example.com"
    folders:
      - "INBOX"
  initial_sync_days: 180
  polling_interval_minutes: 10
  readonly: true
```

密码或授权码不得明文写入普通配置文件。

需要由 Codex 分析合适的本地 Secret Storage 方案。

---

## 2.3 首次历史邮件同步

用户首次连接邮箱时，系统读取一定时间范围内的历史邮件。

默认可以扫描最近：

```text
90 天
180 天
或由用户自行选择
```

首次扫描流程：

```text
连接 IMAP
    ↓
以只读方式打开指定邮箱文件夹
    ↓
按时间范围搜索邮件
    ↓
读取邮件基础信息
    ↓
执行低成本规则过滤
    ↓
读取可能与求职相关的邮件正文
    ↓
解析正文
    ↓
执行招聘邮件分类
    ↓
提取公司、岗位、阶段和时间
    ↓
创建邮件记录和申请事件候选
    ↓
请求用户确认历史申请重建结果
```

首次同步不应直接把所有历史邮件正文永久保存到业务数据库。

建议优先保存：

* Message-ID。
* IMAP UID。
* 邮箱文件夹。
* 发件人。
* 主题。
* 收件时间。
* 内容哈希。
* 是否与求职相关。
* 与申请的关联关系。
* 必要的招聘正文或摘要。

无关邮件应尽量不保存正文。

---

## 2.4 增量邮件同步

首次同步完成后，系统通过定时轮询读取新增邮件。

初期默认：

```text
每 10 分钟同步一次
```

同步频率应可配置。

需要使用以下信息实现增量同步：

* IMAP UID。
* UIDVALIDITY。
* 最后同步 UID。
* 邮箱文件夹。
* Message-ID。
* 内容哈希。

推荐流程：

```text
定时任务触发
    ↓
连接 IMAP
    ↓
以只读模式打开邮箱文件夹
    ↓
检查 UIDVALIDITY
    ↓
查询最后同步 UID 之后的新邮件
    ↓
读取新邮件
    ↓
解析和分类
    ↓
保存同步游标
    ↓
关闭连接
```

系统必须避免：

* 每 10 分钟重新扫描全部邮箱。
* 重复处理同一封邮件。
* 因程序中断而丢失邮件。
* 因 UID 变化而错误跳过邮件。

---

## 2.5 邮件标准数据结构

邮箱 Connector 应将不同邮箱的邮件转换为统一格式。

示例：

```json
{
  "account_id": "mail-account-1",
  "folder": "INBOX",
  "uid": 12345,
  "uid_validity": 67890,
  "message_id": "<example@example.com>",
  "thread_key": null,
  "from": [
    {
      "name": "示例公司招聘",
      "address": "recruit@example.com"
    }
  ],
  "to": [
    {
      "name": null,
      "address": "user@example.com"
    }
  ],
  "subject": "后端开发工程师笔试通知",
  "received_at": "2026-07-22T10:00:00+08:00",
  "body_text": "邮件纯文本正文",
  "body_html": "邮件 HTML 正文",
  "attachments": [],
  "content_hash": "sha256...",
  "raw_headers": {}
}
```

Connector 不直接把该结构写成申请状态。

它应先生成标准 Source Event，交给后续业务管道处理。

---

## 2.6 邮件解析

邮件解析需要处理：

* 纯文本正文。
* HTML 正文。
* Multipart 邮件。
* 不同字符编码。
* 转发邮件。
* 回复链。
* 签名。
* 页脚。
* 邮件中的链接。
* 日历邀请。
* 附件元数据。

初期至少实现：

1. 解析主题。
2. 解析发件人。
3. 解析收件时间。
4. 提取纯文本正文。
5. 将 HTML 转换为可分析文本。
6. 计算正文哈希。
7. 保留必要原始信息用于追溯。

初期附件可以只保存元数据，不必立即解析文件内容。

---

## 2.7 招聘邮件过滤

不能将所有邮件直接发送给大模型。

建议采用分级过滤。

### 第一层：规则过滤

根据以下信息初筛：

* 主题关键词。
* 发件人名称。
* 发件人域名。
* 已知招聘系统域名。
* 邮件正文关键词。
* 邮件是否属于已有申请线程。
* 是否包含笔试、面试、测评、Offer 等时间信息。

### 第二层：轻量分类

判断邮件是否属于：

```text
招聘相关
可能招聘相关
无关
无法判断
```

### 第三层：求职信息提取

只对招聘相关或可能相关的邮件执行详细分析。

---

## 2.8 招聘邮件分类

计划支持以下类型：

```text
application_confirmation
assessment_invitation
written_test_invitation
interview_invitation
interview_reschedule
interview_result
rejection
offer
onboarding
career_event
job_recommendation
follow_up
irrelevant
unknown
```

每次分类应返回：

* 类型。
* 置信度。
* 判断依据。
* 提取字段。
* 是否需要用户确认。

示例：

```json
{
  "category": "interview_invitation",
  "confidence": 0.96,
  "company_name": "示例公司",
  "job_title": "后端开发工程师",
  "event_time": "2026-07-25T14:00:00+08:00",
  "action_required": "参加线上技术面试",
  "meeting_url": "https://example.com/meeting",
  "evidence": [
    "邮件主题包含“技术面试邀请”",
    "正文明确给出面试时间"
  ]
}
```

---

## 2.9 邮件与申请匹配

系统需要将招聘邮件关联到正确的申请。

匹配依据包括：

* 公司名称。
* 公司邮箱域名。
* 岗位名称。
* 申请编号。
* 邮件线程。
* 候选人编号。
* 历史邮件。
* 用户投递时间。
* 已有申请状态。
* 招聘系统名称。

建议匹配流程：

```text
精确申请编号
    ↓
精确公司和岗位
    ↓
公司别名和岗位别名
    ↓
邮件线程关联
    ↓
模糊匹配
    ↓
Agent 判断
    ↓
用户确认
```

匹配不确定时不能直接更新状态。

应创建 Review Task：

> 这封面试邀请可能对应以下申请，请确认。

---

## 2.10 邮件触发申请事件

邮件识别后，系统生成申请事件候选。

例如：

```json
{
  "application_id": "application-123",
  "event_type": "written_test_invited",
  "occurred_at": "2026-07-22T10:00:00+08:00",
  "scheduled_at": "2026-07-25T19:00:00+08:00",
  "source_type": "email",
  "source_id": "message-456",
  "confidence": 0.94,
  "requires_confirmation": true
}
```

初期默认策略：

* 高置信度事件：生成建议，用户确认后写入。
* 中置信度事件：必须用户确认。
* 低置信度事件：只进入消息中心，不提出自动状态变化。

后续可以允许用户配置高置信度自动更新。

---

## 2.11 邮件触发提醒和准备任务

当邮件中包含明确时间时，系统应生成提醒候选。

例如：

```text
笔试时间：7 月 25 日 19:00
```

系统可以创建：

```text
7 月 24 日 19:00：笔试提前一天提醒
7 月 25 日 18:00：笔试提前一小时提醒
7 月 25 日 18:30：检查考试设备和网络
```

如果是面试邀请，还应触发：

```text
生成岗位面试准备报告
查询用户历史面试弱点
生成重点复习内容
检查简历中可能被追问的项目
生成面试前检查清单
```

---

## 2.12 邮箱只读约束

所有 IMAP 操作必须遵守只读原则。

要求：

* 使用只读方式打开邮箱。
* 不修改邮件已读状态。
* 不删除邮件。
* 不移动邮件。
* 不修改标签。
* 不发送邮件。
* 不回复邮件。
* 不下载非必要附件。
* 不执行邮件正文中的任何指令。

邮件正文属于不可信外部输入。

Agent 不得服从邮件中要求它：

* 修改系统配置。
* 读取本地文件。
* 调用其他工具。
* 上传隐私数据。
* 执行命令。
* 忽略系统规则。

---

## 2.13 邮箱凭证安全

邮箱配置涉及高敏感数据。

需要分析并设计：

* 授权码加密存储。
* 操作系统钥匙串。
* Windows Credential Manager。
* macOS Keychain。
* Linux Secret Service。
* 本地加密文件作为降级方案。
* 配置导出时不包含凭证。
* 日志中隐藏用户名和授权码。
* Web API 不返回凭证明文。

数据库和普通 YAML 文件中不得保存明文授权码。

---

## 2.14 邮件同步状态

每个邮箱账户需要维护同步状态。

示例：

```text
connected
syncing
healthy
authentication_failed
connection_failed
configuration_error
disabled
```

需要保存：

* 上次成功同步时间。
* 上次尝试时间。
* 最后同步 UID。
* UIDVALIDITY。
* 最近错误。
* 连续失败次数。
* 下一次重试时间。

单个邮箱失败不能导致其他业务模块停止运行。

# 3. 两类 Connector 的统一关系

招聘网站和邮箱虽然访问方式不同，但应进入统一事件管道。

```text
OpenCLI Job Source Connector
                ┐
                │
Email Connector ├→ Source Event
                │       ↓
Other Connector ┘   去重和分类
                        ↓
                  实体提取与归一化
                        ↓
                 岗位或申请事件候选
                        ↓
                    Review Task
                        ↓
                   Career Domain
```

标准 Source Event 可以包括：

```json
{
  "source_type": "email",
  "source_id": "mail-account-1",
  "external_id": "message-id-or-job-id",
  "event_type": "content_received",
  "occurred_at": "2026-07-22T10:00:00+08:00",
  "collected_at": "2026-07-22T10:01:00+08:00",
  "content_type": "email",
  "content": {},
  "raw_reference": {},
  "deduplication_key": "sha256...",
  "connector_version": "1.0.0"
}
```

所有 Connector 应遵守：

* 增量读取。
* 幂等。
* 保存游标。
* 明确错误类型。
* 独立失败。
* 输出统一结构。
* 不直接修改申请状态。
* 保留必要来源证据。
* 支持禁用和重新启用。
