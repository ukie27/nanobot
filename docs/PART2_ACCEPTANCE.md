# Part 2 用户验收指南：岗位池与可解释匹配

Part 2 已进入 `user_acceptance`。本阶段只验证手动岗位导入、版本化、要求提取和基于已确认事实的匹配；不会调用或开发 OpenCLI，不会扫描招聘网站、创建申请或生成投递材料。

## 1. 升级数据库

在项目根目录执行：

```powershell
.\.venv\Scripts\python.exe -m nanobot career db migrate
.\.venv\Scripts\python.exe -m nanobot career doctor
```

迁移会先为现有 SQLite 创建一致性备份，再从当前 revision（可能是 `20260723_0001` 或 `20260723_0002`）升级。预期 doctor 显示：

```text
DB revision  20260723_0003  20260723_0003  PASS
```

如迁移失败，不要删除数据库；保留完整错误输出和备份目录内容用于诊断。

## 2. 启动

```powershell
.\.venv\Scripts\python.exe -m nanobot career serve
```

打开 `http://127.0.0.1:8765`，侧栏应出现“岗位池”。

## 3. 验收前提

先在“职业档案”确认至少几条真实事实，例如学历、工作年限、Python/Java/SQL 等技能。Part 2 严格忽略 `proposed` 和 `rejected` Fact；如果真实经历仍是待审查状态，匹配结果会把对应要求显示为缺口。

## 4. 建议的岗位文本格式

本阶段默认使用离线确定性提取器。真实 JD 可直接粘贴；保留明确字段和“任职要求”标题有助于稳定提取：

```text
职位：Python 后端工程师
公司：示例科技
地点：上海
工作方式：混合办公
截止时间：2026-08-31

任职要求
- 必须熟练 Python 和 SQL
- 本科及以上学历
- 3 年以上后端开发经验
- 熟悉 Docker 优先
```

## 5. 实际验收步骤

1. 进入“岗位池”，粘贴一个真实 JD 并导入。
2. 打开岗位详情，核对公司、职位、地点、截止时间以及硬性/优先要求。
3. 逐条查看“要求 → 可信证据”：匹配项必须显示真实 confirmed Fact；缺口不得出现虚构经历。
4. 检查硬门槛：存在未满足的硬性要求时，页面必须显示“硬门槛未通过”，即使分项得分较高也不能给出高优先级。
5. 原样再次导入同一岗位，应提示相同内容已存在，岗位仍为 v1。
6. 在同一 JD 末尾增加或修改一条要求后再次导入，应保持同一个岗位并产生 v2；详情中可看到两个内容哈希和版本时间。
7. 修改或确认一条职业事实，回到岗位详情点击“重新分析”；分析历史应增加一条，旧分析中的事实值和版本保持为当时快照。
8. 再导入一个明显不符合学历或经验硬条件的岗位，确认缺口原因清晰。
9. 可选：上传 TXT、Markdown 或带文本层的 PDF 岗位文件；扫描图片 PDF 仍不会 OCR。
10. 可选：输入公开 HTTP(S) 岗位 URL 并点击“确认访问并导入”。只有该显式操作会联网；本机、内网、带凭据、重定向和超限响应会被拒绝。
11. 停止服务并重新启动，确认岗位、版本和分析历史仍存在。

## 6. 本阶段安全与数据规则

- 原始 JD、版本、要求、分析和证据保存在本地 SQLite。
- 粘贴/文件/网页响应默认最大 10 MB。
- 证据引用受数据库外键约束，只能指向真实 Candidate Fact；生成分析时还必须处于 `confirmed` 状态。
- 分析保存 Fact ID、Fact version、Fact value snapshot 和事实集合哈希，档案后续编辑不会改写历史结论。
- 相同公司、职位和地点使用确定性精确去重；跨来源模糊合并不会自动执行。
- URL 获取不跟随重定向，并拒绝解析到非公网 IP 的主机。

## 7. 已知范围边界

- 默认要求提取与事实关联是离线规则实现，复杂、排版混乱或高度隐含的 JD 可能需要后续增强；请记录具体漏提取/误分类原文。
- 当前不提供手工编辑提取字段和要求的 UI；本轮验收重点是收集真实 JD 的提取质量问题，稳定后再决定是否加入人工修正工作流。
- 不自动扫描网站，不开发 OpenCLI Adapter，不创建申请记录，不生成简历或求职信。
